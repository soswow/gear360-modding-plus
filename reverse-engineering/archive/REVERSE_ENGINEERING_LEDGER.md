- The MCP `search_procedures` result found two entries named `CCapImageSetCb::GetStillImageYccData`: thunk `0x3a318` and implementation `0x89358`. The implementation is 2,228 bytes. It reads a position from `pref_rtos` byte `0x1c4f`, checks a slot-ready byte at `0x34294 + slot`, and, when that byte is clear, steps back one slot modulo 25. It copies `0xd70` (3,440) bytes from `0x1c54 + slot * 0xf00` into a `stCAPTURE_IMG_SHARED_SET` argument, advances the read position, and clears the selected ready byte.
- Comparing that with `GetStillImageEncData` confirms a parallel path: encoded data uses position bytes `0x1c50`/`0x1c51`, ready-byte base `0x342ad`, and data base `0x19354`; both use 25-position modulo arithmetic, a `0xf00` (3,840-byte) slot stride, and a `0xd70`-byte copy. The 25-slot ring interpretation is strongly supported by both implementations but remains an inference about the producer's data structure. The code proves bytes are copied into a shared-set structure; it does not yet prove those bytes are the image pixels rather than descriptors or references to another buffer.
- `CAttributeHandler::setCaptureYccImageReady` publishes topic `0x03010001`, and `CAttributeHandler::setCaptureImageReady` publishes topic `0x03010005`, passing a `stCapImageSet*` stored in the handler. This links the YCC/encoded ready events to the publisher topics handled by `CCapImageSetCb::OnCallback`. The setters validate handler state and a non-null pointer; they do not themselves write the image bytes.
